# DEV-TEST — 例行测试（任务级）

## 前置检查

1. 确认 STATUS 为 DEV
2. 确认 TASK.md 中有已勾选 `[x]` 的任务

## 触发时机

- 每完成一个任务后**必须**执行（hooks 会强制提醒）
- STATUS 保持 DEV，不切换阶段

## Agent 调度（强制模板）

**启动轻量独立 TEST subagent，范围限定为单个任务：**

```
Agent({
  description: "例行 TEST - 验证任务 <任务名>",
  prompt: `你是一名 QA 工程师。验证以下任务是否真正完成。

## 验证目标

任务：<从 TASK.md 摘取刚完成的任务名>
Done when：<该任务的 Done when 标准，原文>

## 相关规范

<仅从 SPEC.md 中摘取与该任务相关的部分，如接口定义、数据模型>

## 验证要求

1. 必须将测试代码写入 `tests/` 目录下，不允许直接在终端运行临时命令验证
2. 运行 `tests/` 中对应模块的测试来验证
3. 按 Done when 逐条检查
4. 只验证这一个任务，不扩大范围

## 输出格式

结论：通过 / 未通过
原因：<如果未通过，精确描述问题和复现步骤>

## 未通过时写入 Issue

如果验证未通过，必须将问题写入 issue 文件：

路径：<DOC_ROOT>/issue/issue_devtest_<YYYY-MM-DD>_<seq>.md

格式：
\`\`\`markdown
# 例行测试问题 — <任务名>

**测试类型**：例行 TEST
**验证任务**：<任务名>
**总体结论**：未通过

## 问题列表

### 1. [问题标题]
- **严重程度**：Critical / Major / Minor
- **状态**：Open
- **问题描述**：...
- **复现步骤**：...
- **预期 vs 实际**：...
- **修复建议**：...
\`\`\`

## 禁止

- 不要阅读 dev-doc/session/ 下的文件
- 不要验证其他任务
- 不要建议新功能
- 不要因为 SPEC 没要求的功能缺失而报"未通过"
- 禁止使用系统 /tmp/，临时文件只能放项目 tmp/ 下`
})
```

## 输入隔离规则

| 允许传入 | 禁止传入 |
|----------|----------|
| 该任务的描述和 Done when | 其他任务的信息 |
| SPEC.md 中相关部分（非全文） | 开发过程对话历史 |
| | session/memory/ 记录 |
| | PRD.md |

## 结果处理

- **通过** → 保持 TASK.md 的 `[x]`，继续下一个任务
- **未通过** → 取消勾选（改回 `[ ]`），issue 文件已写入 `dev-doc/issue/`，可用 `/fix` 修复后重新 /devtest

## 为什么需要独立 agent

开发者会无意识避开自己代码的薄弱点。即使是轻量测试，也必须由独立视角验证。"我检查过了没问题"不算验证。
